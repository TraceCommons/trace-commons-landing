Scoring a hackathon from the traces participants produced

A participant uploads only their project's coding-agent traces, hands you the envelope ids that came back, and you pull scores for those ids to rank the competition. Three moving parts, one join key, no schema coupling between us.
Written for the devfolio integration. Verified against trace-commons-server main as of 2026-07-23.

1How the pieces fit

Everything hangs on submission_id — the envelope id Trace Commons assigns each uploaded trace. The participant's upload emits them, devfolio stores them against a hackathon entry, and the score read-back is keyed by them.

Nothing devfolio-specific goes into the trace itself. You own the entry-to-ids mapping and can change it without touching us, and we never need to know what a "hackathon entry" is.

2Scope the upload to one project

By default the contributor CLI treats a developer's whole local corpus as candidates — every coding-agent session on the machine. For a hackathon that is far too much. --project narrows the batch to sessions whose working directory sits at or under one path, matched against the session's real working directory rather than a mangled folder name, so a project literally named my-hack matches correctly.

$ cd ~/code/my-hack
$ trace-commons-contributor submit --project . --manifest ids.json

  3 sessions match ~/code/my-hack
  submitted 7c9f1a2e-4b30-4d81-9f52-1e6a0c33bd77 accepted
  submitted 2ad4e8b1-6c07-4a99-8e13-5b70f2c4a901 accepted
  refused (residual-secret-detected)

  wrote 2 envelope id(s) to manifest

That refusal is the local scrubbing pass doing its job: a session still carrying a credential after redaction is never uploaded, and never reaches the manifest. Sessions are independent, so one refusal does not cost the batch.

3Hand over the manifest

ids.json lists exactly the envelopes that reached the server — freshly submitted and already-submitted alike, refusals and failures excluded. This is the file a participant attaches to, or pastes into, their devfolio entry.

[
  {
    "submission_id": "7c9f1a2e-4b30-4d81-9f52-1e6a0c33bd77",
    "status": "accepted"
  },
  {
    "submission_id": "2ad4e8b1-6c07-4a99-8e13-5b70f2c4a901",
    "status": "already-submitted"
  }
]

already-submitted means the participant had uploaded that exact session before — the id is stable and still valid to score, so keep it. Treat the list as append-only per entry: a participant can re-run submit as the project evolves and give you more ids.

Watch for

--manifest is refused alongside --dry-run. A dry run mints ids locally without uploading anything, so its ids would never exist server-side and you would collect ids that can never be scored.

4Pull scores for those ids

One request, up to 500 ids at a time. Participants each live in their own tenant, and this route reads across all of them, so devfolio makes a single call per batch rather than one per participant.

$ curl -X POST https://ingest.tracecommons.ai/v1/admin/scores-by-submission \
    -H "authorization: Bearer $DEVFOLIO_TOKEN" \
    -H "content-type: application/json" \
    -d '{"submission_ids": ["7c9f1a2e-...", "2ad4e8b1-..."]}'
[
  {
    "submission_id": "7c9f1a2e-4b30-4d81-9f52-1e6a0c33bd77",
    "credit_quality_micros": 284000,
    "perplexity_micros": 12400000,
    "novelty_score_micros": 210000,
    "gate_passed": true
  },
  {
    "submission_id": "2ad4e8b1-6c07-4a99-8e13-5b70f2c4a901",
    "credit_quality_micros": null,
    "perplexity_micros": 9100000,
    "novelty_score_micros": 50000,
    "gate_passed": true
  }
]

Illustrative values — field shapes are exact, numbers are examples sized to the range real traces occupy.

5Reading the scores

credit_quality is the headline: a single graded number in [0, 1] combining how much genuinely new work a trace represents against how substantial it is. It is the field to rank on.

FieldTypeWhat it means
credit_quality_micros int | null Graded credit quality q × 1,000,000, so 284000 is 0.284. The field to rank on. null until the credit-quality pass has scored that trace.
perplexity_micros int How surprising the trace is to the scoring model, × 1,000,000. A content-complexity signal: low values mean thin or boilerplate work.
novelty_score_micros int How distinct the trace is from what has already been contributed, × 1,000,000. This is what catches near-duplicate submissions.
gate_passed bool Whether the trace cleared both the novelty and substance floors. A cheap first filter before you look at q at all.

All scores are integers in millionths — no floats on the wire, so equal scores compare equal and a leaderboard sorts deterministically. When a trace has been scored more than once, you always get the most recent decision.

Size your display for a compressed range

The scale runs to 1.0, but scores are heavily bottom-clustered in practice: the large majority of scored traces land below 0.3, and a genuinely strong entry is nearer 0.3 than 1.0. A leaderboard that renders q as a linear 0-to-1 bar will squash every real entry into the left edge and look broken. Rank on the raw value, but scale the visual to the spread you actually receive — or rank on position rather than magnitude.

7Your credential

devfolio gets a narrow, purpose-built token — a competition read credential that can call this one route and nothing else. It is not an admin token: it cannot read traces, export anything, or write. If it leaks, the blast radius is "someone can read scores for ids they already know".

  • The credential is a signed token carrying role=competition_read_worker.
  • Send it as authorization: Bearer <token>.
  • We issue devfolio's for the hackathon window and rotate it after.

8What never comes back

The read-back returns scores and nothing else. No trace content, no prompts or code, no contributor identity, no tenant. Our own audit log of your reads records only the surface name and how many rows were returned — not which ids you asked about.

One property worth knowing

submission_id is derived from session content, so if two participants somehow upload the byte-identical session, they share an id and one row. The score is a function of the content, so the value is correct either way — but do not read a row as proof of who produced it. Your entry-to-ids mapping is the authority on attribution, not ours.
