1What instance enrollment does

Trace Commons lets an IronClaw deployment contribute redacted agent traces to a shared corpus in exchange for credits. There are two enrollment models, and they coexist:

  • Personal-invite enrollment — an individual user enrolls their own scope with an operator invite. Their traces are attributed to their own device key. This is unchanged by anything in this guide.
  • Instance-wide enrollment — you, the admin, enroll the whole instance once. Every user who has not personally enrolled and has not explicitly opted out contributes under the instance enrollment, attributed per-user via a salted pseudonymous subject (the server never sees raw tenant/user IDs; the salt is random, per-instance, and never leaves the host).

Precedence, enforced by the resolver (resolve_trace_credentials):

  1. A user's own enabled personal enrollment always wins.
  2. A user's explicit opt-out (a per-user policy that exists with enabled=false) blocks the instance fallback entirely — for capture, upload, and credential minting.
  3. Otherwise, an enabled instance policy applies, with a per-user pseudonymous subject.

The contribution pipeline for enrolled users: terminal turns are captured, run through the local redaction pipeline, queued on disk, and a background worker flushes eligible envelopes every 5 minutes (eligibility gates: minimum local score, optional tool-name allowlist, and PII findings held for manual approval by default).

2Before you start

Get from the Trace Commons operator (NEAR AI)

  • An operator instance invite link — https://<host>#<code> (or <code>@<host>). This is all the recommended path needs: the enrollment handshake returns the tenant ID, ingest endpoint, and issuer configuration, trust-anchored to the invite's origin.
  • One invite per instance: near.ai and NEAR Foundation must enroll with distinct invites so they get distinct tenant IDs (see §9).
  • Only if you use the token-based fallback (§3, Path B): the ingestion endpoint URL, issuer URL + allowed hostnames, tenant ID, a workload/bearer token, and — if the server runs with TRACE_COMMONS_ALLOWLIST_SOURCE — a pilot invite code.

Decide your consent posture

Two flags control what enters envelopes after redaction; both default to off and you should set them deliberately, because they apply instance-wide for every inheriting user:

  • include_message_text — redacted user/assistant message text.
  • include_tool_payloads — redacted tool arguments, tool results, and HTTP bodies.

Know your paths

All state lives under the IronClaw base directory (IRONCLAW_BASE_DIR, default ~/.ironclaw):

Path (relative to base dir)What it is
trace_contributions/policy.jsonThe instance enrollment policy (scope None) — what you write in §3
trace_contributions/subject_saltPer-instance random salt for pseudonymous subjects (0600, auto-created)
trace_contributions/device_keys/Instance device keypair (device-key enrollment only)
trace_contributions/queue/Queued redacted envelopes awaiting flush
trace_contributions/users/<scope-hash>/Per-user state: personal policy, records, credits, login-link delivery files

3Enroll the instance

Path A — invite-based device-key enrollment (recommended)

One command, run as the OS user that owns the IronClaw service, on the instance host (host-shell possession is the admin gate):

ironclaw-reborn traces enroll-instance \
  --invite 'https://<trace-commons-host>#<invite-code>'
  # plus, only if chosen deliberately (applies instance-wide):
  # --include-message-text --include-tool-payloads
  # machine-readable output: --json

This performs the device-key onboarding handshake against the operator invite and writes the instance enrollment (trace_contributions/policy.json, auth mode DeviceKey) plus the instance device keypair. The command prints the enrolled tenant, ingest/issuer endpoints, device-key ID, and the user-facing implications; it fails closed — a rejected or expired invite leaves no partial enrollment behind.

Every user without a personal enrollment now contributes under this enrollment, attributed via a salted per-user pseudonym — so credits, submitted-trace inspection, and account login links are all per-user. This is the model the feature was designed for and the right choice for both of your multi-user instances.

Path B — token-based enrollment via opt-in (fallback)

Only for deployments where the operator issues workload/bearer tokens instead of invites:

export TRACE_COMMONS_WORKLOAD_TOKEN=<operator-issued workload token>

ironclaw-reborn traces opt-in \
  --endpoint https://<trace-commons-host>/v1/traces \
  --upload-token-issuer-url https://<trace-commons-host>/v1/trace-upload-claim \
  --upload-token-issuer-allowed-hosts <trace-commons-host> \
  --upload-token-audience trace-commons-ingest \
  --upload-token-tenant-id <your-tenant-id> \
  --upload-token-workload-token-env TRACE_COMMONS_WORKLOAD_TOKEN \
  --upload-token-invite-code <pilot-code-if-required>

The workload-token env var must be present in the service's environment (daemon unit/env file), not just your shell.

Attribution caveat

Per-user pseudonymous subjects are only sent in device-key auth mode. Token-based enrollment attributes all contributions to the shared instance principal: credits pool at the instance level, and per-user account features (login links, submitted-trace inspection, community profiles) act on that shared account. Prefer Path A for any multi-user instance.

4Verify enrollment

# Instance-level policy (the global/scope-None policy)
ironclaw-reborn traces status --json

# End-to-end reachability of the ingest + issuer
ironclaw-reborn traces ingest-health

# Queue diagnostics (per user scope with --user-scope tenant/user)
ironclaw-reborn traces queue-status --json

Then confirm the resolver actually picks the instance policy up for a real user: from that user's WebUI, Settings → Trace Commons should show enrollment/credits rather than the not-enrolled zero state.

5What your users will see

  • WebUI → Settings → Trace Commons: credit totals and explanations, submissions held for manual review (with an Authorize button for PII-flagged envelopes), a per-user list of submitted traces with status and pending/final credit, and — for enrolled users — an "Open Trace Commons account" button.
  • Opening the Trace Commons account: the button mints a one-time login link server-side and opens the contributor's account page in a new tab. This is the path hosted multi-tenant users rely on — no shell or host-file access needed. The link is single-use, expires shortly, is pinned to the enrolled Trace Commons origin, and travels only over the authenticated WebUI response to the user's own browser (never logged, never in chat, never on any model-visible surface). Mints are rate-limited to 10/minute per user.
  • Agent capabilities (all consent-gated with an approval prompt; the agent must ask before acting): trace_commons.status, trace_commons.credits, trace_commons.onboard (personal enrollment), trace_commons.account_login_link, trace_commons.profile_token / profile_set.
  • Agent-path login links are likewise never shown in chat: when minted via the agent capability, the URL is written to a private local file (account_login_link.<uuid>.url, 0600, pruned after ~1 hour) under the user's trace-contribution directory — relevant for self-hosted single users; hosted users should use the Settings button instead.
  • Community profiles (public handle/bio) are a separate, explicit opt-in per user — instance enrollment never publishes anything public on a user's behalf.

6User opt-out — communicate this before enrolling

Instance enrollment is opt-out for users, so tell them before you flip it on. To exclude a specific user (you run this on their behalf — hosted users have no shell):

ironclaw-reborn traces opt-out --user-scope <tenant-id>/<user-id>

With --user-scope this is a scoped-only opt-out: it writes that user's policy with enabled=false and blocks the instance fallback everywhere for them — no capture, no upload, no credential minting — while the instance enrollment and every other user are untouched. The precedence is regression-tested; a later instance re-enrollment does not override it.

Bare opt-out is the master switch

ironclaw-reborn traces opt-out without --user-scope disables the instance-level enrollment itself (plus the owner scope) — every inheriting user stops contributing. Use it only to decommission the enrollment, never to opt out one user.

Suggested user notice

"This instance contributes locally-redacted agent traces to Trace Commons for credits. Redaction runs on this host before anything is stored or sent; message text and tool payloads are [included / not included] per instance policy. You are identified only by a salted pseudonym. To opt out entirely, ask your admin — opting out affects only you, takes effect immediately, and cannot be overridden by re-enrollment."

7Day-2 operations

  • Flush cadence: the background worker submits eligible envelopes and syncs credit status every 5 minutes. Manual kick: ironclaw-reborn traces flush-queue.
  • Held submissions: PII-flagged envelopes wait for per-user authorization (WebUI Trace Commons tab). They never auto-submit unless the policy was created with the PII-review bypass, which you should not enable instance-wide.
  • Credits: ironclaw-reborn traces credit [--json]; users see their own in the WebUI. Final credit lands after the status sync that follows submission.
  • Revocation: ironclaw-reborn traces list-submissions then traces revoke <submission-id>. Revocation flags the submission server-side; local records are status-marked, never deleted.
  • Do not delete subject_salt. Rotating it silently re-pseudonymizes every user — the server will treat everyone as new contributors and per-user credit continuity breaks. Back it up with the same care as the device keys.
  • Backups: the whole trace_contributions/ tree is the local source of truth (policies, keys, salt, queue, records). Include it in host backups; it contains no plaintext secrets other than key material already scoped to this enrollment.
  • Network: outbound HTTPS to the Trace Commons host only. All trace egress uses pinned DNS resolution with private/internal-IP rejection; agent-invoked calls additionally route through the host egress policy layer.

8Security model in brief

  • Redaction happens locally, before storage — the queue on disk already holds redacted envelopes only.
  • Users are pseudonymous to the server via sha256(salt:scope) with a per-instance random salt; raw tenant/user IDs never leave the host.
  • Every agent-initiated Trace Commons action is consent-gated (the model must obtain in-conversation confirmation) and approval-gated (the runtime asks the user), and routes through host network egress.
  • Non-agent network paths (CLI, background flush, WebUI fetches) use hardened HTTP clients: pinned DNS, private-IP filtering, no redirects, bounded response bodies.
  • One-time login links are pinned to the enrolled Trace Commons origin (server-side origin check + client-side http(s)-only guard) and delivered either over the authenticated WebUI response (hosted users) or a private local file (agent path) — never through the model transcript.
  • Explicit user opt-out takes precedence over instance enrollment on every code path.

9Notes for your two instances

  • Distinct tenant IDs. Request separate tenant IDs (and invite codes, if allowlisted) for near.ai and NEAR Foundation from the operator. The tenant ID feeds the upload-claim principal and the scope keys — sharing one would merge the two instances' contributor namespaces and credit accounting.
  • Per-instance salts are automatic. Each instance generates its own subject_salt, so the same human with accounts on both instances appears as two unrelated pseudonyms. That is by design.
  • Users with personal enrollments keep them. Anyone already personally enrolled (e.g. early pilot participants) is untouched by instance enrollment — personal enrollment wins in the resolver.
  • Staged rollout suggestion: enroll the near.ai instance first with include_message_text/include_tool_payloads off, watch a week of queue diagnostics and held-submission volume, then decide the Foundation instance's consent posture with real data.
